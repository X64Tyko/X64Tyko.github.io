## The binary

The industry keeps reaching for a binary: object-oriented programming and entity
component systems as mutually exclusive religions rather than complementary
memory layout strategies.

## The core problem

**OOP dogma.** Deep inheritance hierarchies (`AActor` → `APawn` → `ACharacter`),
heavy pointer indirection, cache invalidation, bloated object headers, and
virtual dispatch overhead paid every frame across non-contiguous allocations.

**ECS dogma.** Purity-first data-oriented design, where every gameplay
interaction gets modelled as a decoupled component query. This takes a real
performance hit on entity mutation (archetype thrashing), plus system
scheduling overhead and a drop in developer velocity as domain encapsulation
disappears.

**The misconception underneath both.** That ECS is inherently faster because of
some magic data parallelism, which ignores what structural edits cost.

## Hardware realities first

L1/L2/L3 cache hits are driven by contiguous memory layout and predictable
access patterns. Structure-of-arrays versus array-of-structures is the decision
that moves the number. Whether you spelled it `struct` or `class` is not.

## Mutation costs and archetype fragmentation

Adding or removing a component at runtime forces reallocation and structural
copies across archetype chunks. Pure ECS excels at homogeneous static batching:
100k projectiles, particles, anything uniform. It degrades under heterogeneous,
stateful game logic: complex status effects, ability attribute aggregation,
anything where entities differ from each other and change shape at runtime.

## The pragmatic hybrid

1. Wrap contiguous SoA allocations behind clean OOP handles and interfaces. The
   layout is data-oriented; the API is not hostile to work with.
2. Use ECS for high-volume, homogeneous pipelines: particles, swarms, anything
   that feeds a compute shader.
3. Use OOP and state machines for low-volume, high-complexity domain entities:
   player controllers, behaviour trees, system orchestration.
